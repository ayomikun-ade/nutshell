# Nutshell — AI Page Summarizer

A Chrome extension (Manifest V3) that pulls the readable content out of any webpage and turns it into bullet-point notes, key insights, an estimated reading time, and a word count — powered by Groq.

Built as a self-hosted, local-install extension: clone, deploy the proxy, load unpacked.

## Features

- **Bullet summary + key insights** generated by Llama 3.3 70B on Groq
- **Brief mode** — switch to a 3-bullet summary when you just want the gist
- **Reading time + word count** calculated from the full article (not the truncated AI input)
- **Copy as plain text** — formatted for pasting into Slack, Notion, anywhere
- **Per-URL caching** with LRU eviction so re-summarizing is instant and free
- **Mozilla Readability** for clean extraction, with a heuristic fallback for non-article pages
- **Neubrutalism UI** — chunky borders, hard shadows, sharp corners
- **Keyboard accessible** — visible focus rings, tab navigation, `prefers-reduced-motion` honored

## Setup

### 1 — Deploy the proxy

The Groq API key never ships with the extension. It lives only in the proxy's environment variables.

1. Push this repo to GitHub.
2. In Vercel: **Add New → Project**, import the repo.
3. **Root Directory:** `proxy/`
4. **Framework Preset:** _Other_
5. Add environment variable `GROQ_API_KEY` (free key at <https://console.groq.com/keys>).
6. Deploy. Note the resulting URL (e.g. `https://nutshell-yours.vercel.app`).

Detailed deployment notes including local development, the request/response contract, and rate-limiting trade-offs live in [proxy/README.md](proxy/README.md).

### 2 — Point the extension at your proxy

Two places need updating with your deployed URL:

- [`background/background.js`](background/background.js), the `PROXY_URL` constant at the top
- [`manifest.json`](manifest.json), the `host_permissions` entry

> The current values are pointed at the developer's deployed proxy. Replace them before installing your own copy.

### 3 — Load the extension in Chrome

1. Open `chrome://extensions`.
2. Toggle **Developer mode** on (top right).
3. Click **Load unpacked** and select the repo root.
4. Pin the Nutshell icon to the toolbar.

That's it — open any article, click the icon, click **Summarize page**.

## Architecture

```
┌───────────┐  SUMMARIZE  ┌──────────────────────────┐  executeScript  ┌──────────────────────┐
│   popup   │ ──────────▶ │   background (worker)    │ ──────────────▶ │ readability + extract│
│           │             │                          │                 │   (in active tab)    │
│           │ ◀────────── │                          │ ◀────────────── │                      │
└───────────┘  {data}     └────────────┬─────────────┘  {text, meta}   └──────────────────────┘
                                       │
                                       │  POST /api/summarize
                                       ▼
                          ┌──────────────────────────┐
                          │ Vercel Edge Function     │
                          │ (proxy/api/summarize.js) │
                          └────────────┬─────────────┘
                                       │  Groq Chat Completions
                                       ▼
                          ┌──────────────────────────┐
                          │ llama-3.3-70b-versatile  │
                          └──────────────────────────┘
```

**Why this split:**

- The **popup** is a thin view layer. It owns UI state (mode, summary, error) and persists the mode preference in `chrome.storage.local`.
- The **background service worker** handles everything that isn't UI: scripting injection, the proxy call, caching, and error normalization. Popups close on blur, so anything async needs to live here.
- The **content extraction** is injected on demand via `chrome.scripting.executeScript` — it does not run on every page load, only when the user clicks Summarize. This is why `activeTab` is sufficient and we don't need a static `content_scripts` declaration.
- The **proxy** is a single-file Edge Function. It's the only thing that ever sees the Groq API key.

**Caching:** the background worker keys cache entries on `<normalized-url>::<mode>` (hash and tracking params stripped) and stores up to 50 entries with LRU eviction. Default and Brief mode summaries for the same URL are cached independently. Wipe via `nutshell.clearCache()` in the service-worker DevTools console.

## AI integration

**Model.** Default is `llama-3.3-70b-versatile`. Overridable via the `GROQ_MODEL` env var on the proxy. Llama 3.3 70B has a 128K-token context window, so even longform articles fit comfortably.

**Structured output.** The proxy uses Groq's `response_format: { type: "json_object" }` to guarantee the response is parseable JSON. The prompt asks for:

```json
{ "bullets": ["…"], "insights": ["…"] }
```

The proxy then sanitizes the result before returning it: only string items, items capped at 240/280 chars, total items capped at 8/4. If the model produces nothing usable, the proxy returns a 502 rather than rendering an empty card.

**Prompt engineering.** Two big levers determine bullet quality:

1. A length **range** (≈18-30 words per bullet), not just a ceiling. A ceiling alone tells the model "shorter is better" and you get headline fragments.
2. An information-density directive plus a bad/good example pair anchored in the prompt:
   - Bad: _"JWST captured images of distant galaxies."_
   - Good: _"JWST captured infrared images of galaxies that existed just 300 million years after the Big Bang, far earlier than previously observed."_

Brief mode swaps in tighter constraints (exactly 3 bullets, no insights).

**Reading time + word count** are computed locally from the full extracted text _before_ it's sent to the proxy. Asking the model for these would be slower, more expensive, and less accurate.

## Security decisions

- **No API key in the extension.** The Groq key lives only in the proxy's Vercel environment. The unpacked extension contains no secrets — `git grep` for `gsk_` and you'll find nothing.
- **Minimal permissions.**
  - `activeTab` — granted only when the user clicks the action button
  - `storage` — for the summary cache and the mode preference
  - `scripting` — to inject the extractor on demand
  - `host_permissions` — restricted to the single proxy URL, not `<all_urls>`
- **XSS-safe rendering.** Every place the popup inserts dynamic text (extracted titles, bullets, insights, error messages) uses `textContent` or `replaceChildren`, never `innerHTML`. Even if Groq or a malicious page returned `<script>alert(1)</script>`, it would render as literal text.
- **Read-only DOM access in the extractor.** `content/extract.js` clones the document before handing it to Readability, so the live page is never mutated. Stripping nav/ads/scripts happens on the clone.
- **HTTPS-only proxy.** The popup rejects non-https tabs early and the manifest only grants permission for the https proxy host.
- **Default-safe CSP.** MV3 forbids inline scripts and `eval` by default; we don't add any exceptions. No `script-src 'unsafe-inline'`, no `Function(...)`, no `eval`.

## Trade-offs

- **Hardcoded proxy URL.** No options page — the URL is a constant in `background/background.js` and a host-permission entry in the manifest. Fine for a self-hosted local extension; would not scale to a Web Store release. An options page with `optional_host_permissions` is the natural next step.
- **No proxy rate limiting or auth.** Anyone who learns your proxy URL can call it and burn your Groq quota. Acceptable for a private install; for production, add per-IP throttling via Upstash Redis or a shared-secret header. See [proxy/README.md](proxy/README.md) for the full discussion.
- **Single LLM.** No fallback if Groq is down. A multi-provider fallback (OpenAI, Anthropic, etc.) would add resilience but doubles the integration surface.
- **Heuristic fallback is rough.** When Readability returns nothing, the heuristic picks the densest text container and strips obvious chrome — works for most non-article pages but can grab sidebars on poorly-structured sites.
- **No incremental rendering.** The popup waits for the full proxy response before showing anything. Streaming would feel snappier on long articles but adds complexity to the popup-background-proxy pipeline.
